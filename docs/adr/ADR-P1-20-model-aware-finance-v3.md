# ADR-P1-20 — Model-aware finance version V3 and atomic live screening

- **Status:** Accepted for implementation, Spec 08 task 8.3 (2026-11-11). First persistent use of `InferenceEvidenceV1` (format 1, unchanged from ADR-P1-19).
- **Scope:** `src/Revenant/Timeline/ModelLedgerFinance.cs`, `src/Revenant/Intelligence/RiskPolicy.cs`, `src/Revenant/Payments/PaymentLedgerStore{,.Screening,.Cases}.cs`, `ScreeningWorker`, `RevenantLedgerService.OpenRunAsync`, `src/Revenant/Projection/{ModelLedgerProjector,LedgerProjector,LedgerProjectionWorker}.cs`, `src/Revenant/Api/RevenantLedgerApi.cs` (registration), `src/Hosts.Worker/Program.cs`, `scripts/db/migrations/revenant/0008_model_aware_screening.sql`, one additive enum value in `src/Revenant/Finance/PaymentLifecycle.cs`. No change to `Marrow.*`, `Revenant.Contracts`, the OpenAPI document, `timeline-ui` or Ghost Lap.
- **Related:** ADR-P1-17 (V2; "learned evidence that the reference cannot express is `/3`"), ADR-P1-18 (tenant staff, four-eyes), ADR-P1-19 (`risk-features-v1`, `InferenceEvidenceV1`).

## Context

ADR-P1-17 froze the V2 fact kinds and made the V2 Screening fact evidence-free: its outcome is re-derived from policy v7. A learned score cannot be re-derived on replay (no inference may run in a reducer), so the score must be a recorded input of the screening step. That changes what a Screening fact means, so it is a new version (ADR-P1-17 decision 4).

## Decision

1. **Version key.** `revenant-finance` / `revenant-finance-reducer/3` / `revenant-finance-fact/3` / `revenant-finance-state/3` / `revenant-finance-context/3` (`ModelLedgerTimelineVersions.V3`), a third engine shape beside V1 and V2. V1 and V2 registrations are unchanged (asserted). A run records its family in `scenario_run.finance_version` when it is opened (`RevenantLedgerService.OpenRunAsync(..., modelAware: true)` or the store's `financeVersion` argument); `scenario_run` accepts no UPDATE, and migration 0008 restricts the column to the `/2` and `/3` values. A V1/V2 history can never become V3; re-opening a run id with another family is `ConflictingDuplicate`. The HTTP open route still opens V2 runs (no API contract change).
2. **Pinned policy.** `RiskPolicyCatalog.V1` = `v7-base+ml-risk-v1`: base policy v7 (`PolicyCatalog.RefOf(V7)`) and the exact `RiskModelIdentity` of the committed 8.2 artifact (`revenant-risk-fasttree-fixture/1`, artifact SHA-256 `c13491fe...d3de`, manifest SHA-256 `00431188...658a`, ML.NET 5.0.1, `risk-features-v1`, threshold 257,796 PPM). Every V3 run uses it. A different artifact or threshold is a new policy id. The V3 context (`ModelLedgerContext`, canonical format 1) stores scenario/manifest/reducer/base policy/review policy plus the risk policy id, all model identity fields, the normalization id and the threshold; decoding re-resolves every pin and fails closed.
3. **Combined screening input.** A V3 Screening fact's payload IS the canonical `InferenceEvidenceV1` bytes (they name run, intent, amount, currency, as-of and screening positions); payload schema `revenant-inference-evidence/1`; the fact's `FactEvidenceRef` is `(revenant-inference-evidence/1, SHA-256(payload))`. The intent bytes are the earlier, immutable `PaymentIntent` fact; the evidence binds to it (`CheckBinds`). So the screening transition cannot be applied before, or without, its evidence. Migration 0008 enforces the shape in PostgreSQL (RV010): V3 Screening facts must carry it, V2 Screening facts and every other kind must not.
4. **Pure reducer.** `ModelLedgerReducer` delegates every non-Screening fact to the frozen V2 `FinanceLedgerReducer` under the pinned V2 base context, so intake, review (four-eyes), settlement and return keep their Spec 07 semantics. For Screening it checks: evidence present and hash-matched; decodes strictly; payment is Initiated; evidence binds to the intent and to this fact position (`ScreeningFactSeq = fact_seq`, `AsOf = fact_seq - 1`); model/policy/threshold equal the context pins; `SourcePostedBeforeMinor` equals the source account's posted balance in this state (causal input check); the recorded base decision equals v7 recomputed here (Clear iff no v7 reason; funds are a ledger consequence, not a policy decision, so the base kind is Clear or Held). It then applies the recorded final decision: a v7 reason keeps precedence; a base-clear payment with `scorePpm >= thresholdPpm` is held with the new `PaymentReason.MlRiskHold` (live text `ml_risk_hold`); any hold reserves and opens a case when available funds cover it, else Held → Rejected(insufficient), exactly as V2. No model, I/O, clock or float scoring. State = V2 state bytes + an integer `LearnedScreening` summary per screened payment.
5. **Live adapter (Worker).** `PaymentLedgerStore.ScreenBatchAsync` resolves the pinned scorer once per batch through `RiskModelProvider` (verify manifest/checksum/schema/package, then require identity == pin; cached after success, retried after failure). For a V3 payment, inside the single screening transaction and in the documented lock order (payment row, source account `FOR NO KEY UPDATE`, run cursor `FOR UPDATE`), it reads the committed posted balance and `last_fact_seq`, builds `risk-features-v1`, scores it with `ITransformer.Transform` (no shared `PredictionEngine`), quantises once to PPM and freezes the evidence for position `last_fact_seq + 1`. Because both locks are held to commit, the inputs cannot change between scoring and commit; the appended fact sequence is asserted equal to the evidence position. Steps, hold, case, outbox events, the evidence-bearing fact and its audit link commit together. Scoring is ~microseconds (8.2 measurement) and is the only thing done while the cursor lock is held beyond the existing V2 work.
6. **Fail closed.** If the pinned model is unavailable or does not verify, V3 payments are not selected (they stay Initiated, no decision/fact/hold/case, the run cannot close: `RunNotQuiescent`), V2 runs continue, and the Worker logs the typed failure. A per-payment feature or score failure (`FeaturesIncompatible`, `ScoreNotFinite`, `ScoreOutOfRange`) throws `RiskScreeningUnavailableException`, the transaction rolls back and the Worker backs off. There is no rules-only fallback inside a V3 run.
7. **Projection and verification.** `ModelLedgerProjector` mirrors the V2 projector (same operation keys, fact `k` at position `k`, payload hash check, close-then-verify) on the V3 engine, and additionally reconciles each recorded final decision with the live Screened → Held reason. It uses only the restricted replay login and never loads a model. The V2 projector refuses V3 runs (`NotDurableV2`). The Worker host registers both engine shapes; the projection loop catches up both families.

## Consequences

- One-screening-per-payment (0005) plus the evidence trigger make a second or evidence-free screening of a payment impossible; a crash after commit leaves a committed decision and the payment is never re-selected, so no second score is computed.
- `PaymentReason` gains `MlRiskHold = 6`. V1/V2 never produce it; existing values and every V1/V2 byte and hash are unchanged (V1/V2 golden tests pass unchanged).
- `ScreeningOutcome` gains an optional `Evidence`; `PaymentLedgerStore` gains an optional `RiskModelProvider` constructor argument; `OpenRunAsync` (store and service) gain optional arguments. All existing callers compile unchanged.
- `LedgerProjector` read helpers became `internal static` (behaviour unchanged) so the V3 projector reuses them.
- Branch inference, cold replay with predictor disabled across processes and model-aware forks are 8.6; anomaly and explanations are 8.4; Spec 09 owns analyst continuation.

## Alternatives rejected

- *Carry evidence in V2 by filling `FactEvidenceRef`*: V2 Screening facts are defined as evidence-free and decided by v7 alone; a V2 replay would ignore the score and disagree with the live ledger.
- *Append the intent, then attach evidence in a later step*: forbidden by the design (screening before its evidence).
- *Revalidate by re-reading after scoring*: holding the account and cursor locks while scoring is simpler and strictly stronger; the cost is microseconds.
- *Payload = intent id + evidence*: redundant; the evidence already names the intent and the DB check becomes a plain hash equality.
