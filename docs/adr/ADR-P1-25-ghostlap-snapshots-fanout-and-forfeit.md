# ADR-P1-25 — Ghost Lap snapshots, per-recipient delivery, resync and forfeit scheduling
- **Status:** Accepted at Spec 10 task 10.3. Implemented and locally tested; real-network and real-browser behaviour is NOT proven (see the evidence document).
- **Scope:** what the authoritative loop publishes to clients, how it is delivered without ever waiting on a client, how a client recovers, and when a vanished competitor is forfeited. Not in scope: rules (ADR-P1-22), ingress (ADR-P1-23), authority and terminal fence (ADR-P1-24, task 10.4 completes it).
- **Evidence:** `docs/architecture/10-ghostlap-snapshots-and-network.md`, `tests/GhostLap/Multiplayer/{ForfeitGraceTests,SnapshotFanoutTests}.cs`, `tests/Integration/GhostLap/GhostLapSnapshotTests.cs`.

## Decisions
1. **Read side.** `MatchFeed` is owned by the match loop (single writer). Every tick adds a `TickFrame` (that tick's resolved events) to a chain cut at `EventRetentionTicks` (300). A snapshot is published every `SnapshotIntervalTicks` (2) ticks and always on the final tick, on a forfeit and on a newly observed disconnect. A reader takes ONE volatile reference (`PublishedSnapshot`: state plus the chain head of the same tick), so state and event boundary cannot disagree. No lock, nothing to wait on.
2. **Identity.** A snapshot names `(MatchId, GenerationId)`, a `Sequence` (count of published snapshots, gaps allowed) and a `Tick`. An event is `(Tick, Index)` inside that identity (index = position in the tick's resolved order, a phase 0 forfeit first). Generation ids are opaque: clients compare them for equality only. The lifecycle (`Running`, `PendingFinalization`, `Aborting`, `Aborted`, `Unverified`) is an immutable (version, status) pair that rides on every frame; the version only rises.
3. **Delivery.** One sender task per connection (`MatchRecipient`). The loop only wakes it. Snapshots are not queued: the sender reads the newest one when it is ready, so a slow client drops stale snapshots by construction (counted exactly). The events a client has not been sent travel with its next frame (per-recipient cursor), so coalescing loses no cue that is still retained; if the cursor fell off the retained tail the frame is a resync baseline and says `Truncated`. Acknowledgements are cumulative and per connection: a newer one replaces an unsent older one, an older one never replaces a newer one. Rejections are reliable, ordered and bounded (`ControlQueueCapacity` 64); overflow drops the newest and one `control_overflow` notice reports how many. A lifecycle change forces a frame, so a terminal status is never coalesced away. Each send has a time limit (`SendTimeoutMilliseconds`, 3 s); exceeding it aborts that connection only (competitor: the normal disconnect path with grace; spectator: gone). Nothing is sent once the process is no longer the authority. The single serial delivery pump of task 10.2 is removed. The owner's notice pump sends concurrently with the same limit.
4. **Resync.** Hub method `Resync` (read-only, so spectators may call it, and it works while the caller's input stream is open) returns a frame with `IsResync`, the retained event tail and the caller's own view (`Role`, `Slot`, `ControllerEpoch`, `CanControl`, `AppliedSeq`). It becomes the recipient's baseline; the pushed stream continues from it without repeating a cue. `AppliedSeq` is the sequence floor as of the newest resolved tick, which can be newer than the snapshot (an acknowledgement may be delivered before the next snapshot). A rejection from the loop also carries `SequenceFloor` and the evaluating `Tick`.
5. **Client filter (reference: `SnapshotFilter`).** Inside one (match, generation) a pushed frame must not lower `(lifecycle, sequence)` and must raise one of them; a resync may repeat both. Another match or generation is discarded unless it is a resync, which replaces the baseline (this is how a rematch is adopted). Events apply once by key; a hole is reported as a gap (cues lost, state exact).
6. **Forfeit scheduling.** The loop reads each slot's controller once at the start of tick `t`. A slot unconnected at that read for the first time starts grace at `D = t` and gets the Spec 06 server neutral. It is forfeited in phase 0 of `F = D + 450` if still unconnected at the read of `F`; a controller present at that read keeps the slot (a takeover processed before `F` resolves wins); a later one is spectator-only (its items are refused `forfeited`, its frames say `CanControl = false`, and it is told once with a `forfeited` control notice). A reconnect clears the grace; a later disconnect starts a new one. The engine starts with every slot counted as connected, so a controller missing at the first tick is a disconnect observed at that tick. The grace is a rules-profile constant (`MpRulesProfile.GraceTicks`), not configuration.
7. **Liveness.** The Ghost Lap hub has its own `KeepAliveInterval` (5 s) and `ClientTimeoutInterval` (15 s) through `AddHubOptions<GhostLapHub>`; a client that sends nothing for 15 s is closed by the server, which is how a half-open connection or a suspended tab becomes a server-observed disconnect (the start of grace). **Client contract:** ping at most every 5 s (the library default of 15 s would close an idle spectator or lobby tab). Validated at startup: timeout at least twice the keep-alive.
8. **`ghost-mp-net-v0` review.** The window (a client tick from 4 behind to 2 ahead of the applying tick), the six-tick hold and the 30 Hz / 2-tick snapshot cadence are kept unchanged: they are `GameRulesV1` constants shared with `ghost-v1`, which this task does not touch, and the measurements (evidence document) show typed refusals of 1.0 to 2.7 % at 50, 150 and 300 ms RTT with jitter and spikes. The v0 text needed one amendment, a client rule, not a server change: the aim estimate must be closed-loop (below).
   - Start from RTT 0 (an input aimed too early is accepted down to 4 ticks late; one aimed too far ahead is refused and can never be acknowledged).
   - Correct the offset from the `Tick` of every `late_tick`/`future_tick` refusal and from every acknowledgement, targeting the window centre (-1), at most once per round trip.
   - Repeat a Burst press until it is acknowledged (a refused press leaves the latch released, so the next pressed item is the edge).

## Consequences
- `IMatchPresence` gained `ViewerAttached/Detached` and `Activate(..., viewers)`; `IActiveRoomOwner` gained `RoomOf`; `InputRejection` gained optional `SequenceFloor` and `Tick`; `MultiplayerOptions.OutboundCapacity` was removed (no longer meaningful). All additive for clients.
- Per-send cost is two small allocations (linked token source and a closure). Whether that matters is a task 10.5 question.
- The in-memory test host applies no transport backpressure (a client that read nothing was still "sent" 229 snapshots), so the send-timeout cut is proven at the fan-out level with a gated transport, not over SignalR. Real TCP saturation is a task 10.6 check.

## Rejected alternatives
- A bounded per-recipient snapshot queue: it would hold stale state and then need a policy for which to drop. Reading the newest at send time has no backlog to manage.
- Group broadcast for spectators: one slow member delays the whole send. Per-connection senders cost an extra task per spectator (capped at 8 per room).
- A forfeit on explicit Leave: ADR-P1-22 defines forfeit by disconnect and grace only; a voluntary leave of a running match stays refused (`wrong_phase`) until a rule says otherwise.
