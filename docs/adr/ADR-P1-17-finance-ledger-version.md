# ADR-P1-17 — Additive finance history version for durable ledger runs

- **Status:** Accepted for implementation, Spec 07 task 7.2 (2026-11-11). Review again at task 7.5 when the first V2 Timeline history is created.
- **Scope:** `src/Revenant` (finance version identifiers, fact envelope, payment persistence), `scripts/db/migrations/revenant/0002_payment_intake.sql`. No change to `Marrow.Timeline`, `timeline-ui` or any frozen shared contract.
- **Related:** ADR-P1-04 (inputs and upstream facts are replayed, decisions are derived), ADR-P1-05 (one engine, branch suffix), ADR-P1-06 (atomic Postgres ledger), ADR-P1-07 (version-pinned ML evidence).

## Context

Spec 05 shipped a pure finance reducer under one Timeline version key (`revenant-finance-reducer/1`, input `revenant-payment-intent/1`). Its histories are built in memory from a generated scenario and carry only exogenous `PaymentIntent`s. Spec 07 adds a durable live ledger, where payments, holds, approvals, returns and settlement are committed in PostgreSQL. Later work (7.4 review and return, 7.5 parity and replay, 08 inference evidence, 09 counterfactual branching) needs a Timeline history of that live run that can be rebuilt and verified against the live ledger. V1 bytes, hashes, reducer behaviour and the v7/v8 policy identities are pinned by tests and cannot change.

## Decision

1. **A new version family beside V1, for newly created durable runs only.** Identifiers (`Revenant.Timeline.FinanceLedgerVersion`): domain `revenant-finance`, reducer `revenant-finance-reducer/2`, input `revenant-finance-fact/2`, state `revenant-finance-state/2`, context `revenant-finance-context/2`. V1 stays registered and untouched. A durable run records its family in `revenant.scenario_run.finance_version`. No V1 history is migrated or rewritten. A fork inherits its source's key; substituting a context cannot change it (the existing Timeline rule).
2. **Ordered canonical facts.** A *fact* is an externally committed input: today a `PaymentIntent`, later (task 7.4, before any V2 history exists) the canonical review decision and return instruction. Decisions, holds, reservations and settlement results are derived and are never facts. Each fact is stored in `revenant.finance_fact` with a run-local, gap-free `fact_seq`, its canonical payload bytes, their SHA-256 and the payload schema. The fact, the payment state step, the trail row, the command record and the outbox event commit in one PostgreSQL transaction. The order is assigned while holding the run's `run_cursor` row `FOR UPDATE`, so `fact_seq` equals commit order; a deferred database constraint rejects any fact that is not exactly the cursor's next value. Intake also requires a strictly increasing logical `Sequence` and a non-decreasing business time, which is what the V1 reducer already demands of its input. The wire form of one fact is `FinanceFactCodec` (format 1: kind, sequence, payload schema, payload, optional evidence reference); unknown kinds, truncation and trailing bytes fail closed.
3. **Restartable, idempotent Timeline projection (built in 7.5).** The projector reads `finance_fact` in `fact_seq` order and appends fact `k` as Timeline position `k` of the run's V2 history, with a deterministic operation key derived from `(ScenarioRunId, fact_seq)`, so a retry or a restart after a crash between the live commit and the projection re-applies nothing. Its progress is the history's own `LastPosition`, checked against `run_cursor.last_fact_seq`; there is no second mutable cursor to drift. The projection commits separately from the live transaction and may lag. A source history becomes `Verified` only after catch-up (`LastPosition = last_fact_seq`) and reconciliation of recorded decisions, statuses, reservations and posted balances against the live ledger under the recorded policy. The replay role can read facts and cannot write any live table.
4. **Minimum future-evidence boundary.** A fact may carry an opaque `FactEvidenceRef(schema, sha256)`; the database stores it as an all-or-nothing nullable pair. Spec 07 neither creates nor interprets it. Spec 08 owns concrete evidence, normalization and model integration. If finalized 08 evidence cannot be expressed through this reference, the answer is a new explicit version (`/3`) with new source and branch keys. Historical bytes are never mutated.
5. **The set of fact kinds is open only until the first V2 history exists.** Task 7.4 may add the review and return kinds. After a V2 Timeline history has been created in 7.5 the set is frozen and any new kind is a new version.

## Consequences

- V1 comparisons (v7 source, v8 branch) are unaffected and remain supported. Alternative-policy parity is not required for V2 live-source verification.
- 7.2 delivers the identifiers, fact envelope, ordering and persistence. It does **not** register a V2 reducer, codecs or resolver: `FinanceTimelineVersions.All` still lists only V1, because a V2 reducer without review and return semantics would be a guess. Tasks 7.4 and 7.5 complete and register it.
- The generic payment transition command refuses any step that enters or leaves `Settled` (`PostingRequired`); settlement and compensating return are task 7.3.

## Alternatives rejected

- *Extend V1 in place* (new input kinds under `/1`): would change V1 canonical bytes or force V1 readers to accept data they never produced.
- *A second reducer outside the Timeline engine*: forbidden by the spec; two replay authorities.
- *Project from the ledger and payment tables directly*: those hold derived decisions and balances, which ADR-P1-04 forbids as replay input.
- *Order by wall clock or by arrival in the projector*: not deterministic after a restart; commit-order sequence assigned inside the live transaction is.

## Task 7.5 addition (first V2 history; review requested above)
- **Ordering facts for system steps.** Concurrent LiveOps workers decide when a payment is screened and in which order settlements commit, and both change balances. Two fact kinds were added before the first V2 history exists (decision 5): `Screening = 4` and `Settlement = 5`, payload `revenant-screening/1` / `revenant-settlement/1` (`PaymentStepCodec`: the intent id only). They record *which payment, at which point of the commit order*; the outcome (hold, clear, reject; settle or return for insufficient funds) is still derived by the reducer from the pinned context, so an alternative-policy branch can diverge. `revenant/0005_audit_projection_relay.sql` widens the kind check and allows at most one of each per payment. **The kind set is now frozen**; any further kind is `/3`.
- **Production path into Held.** `PaymentLedgerStore.ScreenBatchAsync` (run by the Worker's `ScreeningWorker`) is the only fact-recording screening step. A released (Approved) payment is cleared and settled by the settlement worker in one transaction. Generic `TransitionAsync` steps still exist for the earlier task tests but record no fact; a run moved by them does not reconcile and is never verified (tested).
- **Lock order** for every step that changes availability: payment row(s), then account rows (`FOR NO KEY UPDATE`, id order), then the run cursor, then the audit head. The case rejection now locks the source account before the cursor, so fact order agrees with every availability change.
- **Reducer and registration.** `FinanceLedgerReducer` (pure, `Revenant.Timeline`) with `LedgerFinanceState`/`LedgerFinanceContext` and canonical codecs, registered as `FinanceLedgerTimelineVersions.All` (key `revenant-finance` / `revenant-finance-reducer/2` / `revenant-finance-fact/2` / `revenant-finance-state/2` / `revenant-finance-context/2`), a separate engine shape beside V1. The live screening policy of V2 runs is pinned as policy v7 (`LedgerFinanceContext.LivePolicy`, stored in each history's context); the review policy version is pinned too. The fold's business clock starts at 0, like the live run cursor.
- **Projection and verification.** `LedgerProjector.CatchUpAsync` (Worker loop) appends fact `k` at position `k` with operation key `revenant-ledger-step/{run}/{k}` (source key `revenant-ledger-source/{run}`); progress is the history's last position. `VerifySourceAsync` compares the replayed state with one repeatable-read snapshot of the live ledger (statuses, full trails, versions, reservations, hold status, case status, postings, posted and reserved balances) and only then calls `CompleteAsync`. A Verified source accepts no further facts (`FactsAfterVerification`); verifying is therefore an explicit step after a run is closed.
- **Compatibility check (performed).** V1 files (`FinanceReducer`, `PolicyConfig`, `FinanceProjectionState`, `FinanceTimeline{Adapter,Codecs,Versions}`), `Marrow.Timeline` and `Marrow.Kernel` have no diff; `FinanceTimelineVersions.All` still lists only V1 (asserted). V1 golden/hash tests (`FinanceTimelineCodecTests`, `FridayRingTimelineTests`, `HandoffContractTests`, `PolicyAndLifecycleTests`) pass unchanged. OpenAPI/TS changed by one added route and DTO (semantic diff against HEAD: nothing removed or changed).

## Spec 07 exit review addition (run closure and read projection)
- **Run closure is now defined and enforced in PostgreSQL** (`revenant/0007_run_closure.sql`, `PaymentLedgerStore.CloseRunAsync`). `run_cursor.closed_fact_seq` is set once, in a transaction holding the cursor row lock that every fact append also takes. A later intake, screening, review decision, settlement or return advances the cursor, is refused by the trigger (`RV009`) and rolls back with its step, posting and outbox rows; a payment of a closed run also accepts no insert or status change. Closing is refused (`RunNotQuiescent`) while a payment is Initiated, Screened, Approved or Cleared; Held payments may remain Held. `LedgerProjector.VerifySourceAsync` now requires a closed run (`RunNotClosed`) and `closed_fact_seq == last_fact_seq == projected position`. Before this change nothing prevented a live fact after a Verified source (the projection only reported `FactsAfterVerification`). A step that records no fact (the test-only generic `TransitionAsync`) is guarded by a lock-free read of the closed flag, so a transition already in flight when the close commits is not serialized; such runs still fail reconciliation.
- **Compatibility:** additive column, one trigger function replaced with the same checks plus the closed check, one new trigger, additive enum values (`RunClosed`, `RunNotQuiescent`) and one additive projection error. No V1 or Timeline file, no fact kind, no codec and no historical byte changed; the OpenAPI document is unchanged (`generate.sh --check` passes).
- **Read projection (R07.09)** (`revenant/0006_read_projection.sql`, `RevenantEventProjection`, `AddMarrowInboxConsumerService`). The Worker consumes `revenant:events` with the existing `RedisStreamInboxConsumer` (inbox row and effect in one PostgreSQL transaction, acknowledgement after commit, reclaim of idle entries, dead-letter after the delivery bound). Effects: `payment_view` (strictly higher version wins), `hold_view` (Active to terminal only), `posting_view` (one immutable row per ledger group). The role `revenant_read_projector` (granted to `sands_worker`, which already cannot write any ledger table) may write only those views and insert into the inbox. Review-case events are recorded in the inbox and not projected. The views are derived data and never the authority.
