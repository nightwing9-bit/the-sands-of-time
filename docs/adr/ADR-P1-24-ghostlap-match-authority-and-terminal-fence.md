# ADR-P1-24 — Ghost Lap match authority, start receipt and terminal fence
- **Status:** Accepted at Spec 10 task 10.2. Implemented and tested locally (evidence in `docs/kiro-log.md`). The result commit and `MatchFinalizedV1` outbox (10.4), snapshots, reconnect resync and forfeit scheduling (10.3) are NOT part of this decision's implementation. Task 10.4 completed item 4 and replaced item 9: see ADR-P1-26 (`Started -> ResultCommitted` with result and outbox in the same transaction, same lock order).
- **Scope:** who may run a live multiplayer match, how a match starts durably, how its tick loop is scheduled, and how a stale process is kept from deciding a match. Gameplay rules are ADR-P1-22; ingress is ADR-P1-23.

## Decision
1. **One guard, reused.** The process-level exclusivity guard is the existing `RealtimeInstanceGuard` (Marrow, unchanged): session advisory lock on a dedicated non-pooled connection. Ghost Lap adds no second guard. `GhostLapRealtimeAuthority.IsValid` = guard held and not lost AND this process's durable generation is registered and not seen retired. Every tick and every gameplay delivery reads it (volatile reads).
2. **Durable process generation** (`ghostlap.realtime_generation`, migration `ghostlap/0003_mp_authority.sql`). At most one `Active` row (unique partial index). At host start, after the guard holds the lock, `GhostLapGenerationService` registers the generation id that the room owner seals into every round; in the SAME transaction it retires every other generation and aborts every `Started` receipt of a retired generation (`abort_reason = generation_retired`). The host refuses to start if this fails. A monitor re-reads the row every `GenerationCheckMilliseconds` (default 2000); seeing `Retired` withdraws authority, closes Ghost Lap connections and stops the host.
3. **Start receipt before running** (`ghostlap.match_session`). `MatchRegistry.AdmitAsync` inserts the receipt (sealed config digest, seed, rules/layout identity, layout fingerprint, opaque `rating_algorithm_id`, roster subjects in slot order, generation) and answers `Admitted` only after the commit. The insert trigger share-locks the generation row and refuses a non-Active generation (SQLSTATE `GL002`). An identical retry returns `AlreadyStarted` (acknowledgement loss); a different config under the same match id is a `Conflict`, never an overwrite; a terminal match id is `Closed`, after which the room seals the next ordinal (fresh match id and seed). The receipt commit is not cancelled by the room's admission timeout; a committed receipt the room never activates is aborted (`not_activated`).
4. **Terminal fence and lock order.** Every terminal write locks the receipt row (`FOR UPDATE`) first, then share-locks the generation row and requires it Active. Retirement locks the Started receipt rows first, then updates the generation rows. Task 10.4's finalizer must use the same order. Whoever locks a receipt first decides it; the other sees the committed decision. In 10.2 the trigger permits only `Started -> Aborted`; `ResultCommitted` is reserved for the 10.4 migration that adds the result and outbox rows to the same transaction. Identity columns are immutable even for the schema owner; no DELETE/TRUNCATE.
5. **One loop per match, one mailbox per room.** `MatchRegistry` owns every match of the process. Each match has one `MatchEngine` (bounded mailbox, `MailboxCapacity`, refuse-when-full) and one `MatchDriver` task. Hub methods contain no game logic. Socket readers only enqueue. The loop re-reads each slot's controller (epoch and connection) when it applies an input, so items queued by a superseded or closed controller never affect the world. Admission at application time is the unchanged Spec 06 `InputAdmission` (strictly newer sequence, late 4 / lead 2 ticks, quantized vector) plus multiplayer checks (connected, epoch, connection, forfeited, `MaxInputsPerSlotPerTick`). All admitted inputs of a tick go to the reducer in sequence order: the highest sequence sets direction, the existing latch gives at most one Burst per tick, and a press-release inside one tick is one Burst.
6. **Reducer.** `ghost-mp-v1` = phase 0 (forfeits due this tick) + the ONE ghost-v1 phase implementation (`GhostLapPhases.Resolve`) with a participation mask. ghost-v1 calls it with no mask; its goldens are unchanged. State schema `ghost-mp-state/1` = rules id + ghost-v1 world bytes (embedded, codec unchanged) + forfeit ticks; hash = SHA-256 over (schema, bytes). No multiplayer state or input is archived.
7. **Scheduler.** Tick k is due at `start + ceil(k / 30 s)` on the server monotonic clock; the tick count, never wall time, drives the game. When late, at most `CatchUpTicksPerIteration` (3) ticks run back to back, then the loop yields; no tick is skipped and movement is never scaled by elapsed time. Overload = backlog above `LateAlarmTicks` (2) continuously for more than `OverloadSustainedMilliseconds` (2000), or backlog above `OverloadMaxBacklogTicks` (150). Overload, authority loss and host stop end the loop and request a fenced abort (`overload`, `authority_lost`, `host_stopping`) with bounded retries; status is `aborted` only after a durable Aborted decision, otherwise `unverified`. These values are initial policy, not measurements (10.5 measures).
8. **Off the critical path.** A tick does pure CPU work and hands acknowledgements/rejections to a bounded drop-oldest channel (acknowledgements are cumulative). `GhostLapMatchDeliveryPump` delivers them and drops everything once authority is invalid. No SQL or socket write is awaited inside a tick.
9. **End of round in 10.2.** Tick 2700 resolves all phases and the match reports `pending_finalization`. No result row, winner or rating exists; until 10.4 the receipt stays `Started` and the next generation's retirement aborts it. That is an honest unrated outcome, not a result.

## Stale-authority interval (accepted, bounded)
After a silent loss of the guard session, the old process keeps ticking and acknowledging until its guard probe (`Realtime:InstanceLockCheckSeconds`, default 5 s) or its generation monitor (after a successor retired it) notices. During that interval it cannot start a match (insert refused) or decide one (receipt already Aborted by the successor's retirement). Its gameplay feedback in that interval is provisional and has no durable effect. Tested with the probe at 60 s (`GhostLapMatchTests`).

## Contract compatibility
Additive only: `RoomView.MatchStatus` (optional, last positional parameter), `InputAck`, client method `InputsApplied`, `MatchStatuses`, new `GhostLapFailure` codes, `StartAdmissionOutcome.Closed`, `AdmittedInput.ConnectionId` (defaulted). Phase value `start_admitted` is unchanged; it now means "receipt committed". No TypeScript twin exists yet (10.6). `sands_realtime` gains `ghostlap_mp_runtime`; no other login changes.

## Rejected alternatives
- A second advisory lock or a lease table as the guard: duplicates the Marrow guard and is still not a fence.
- Checking the generation in the database on every tick: synchronous I/O in the reducer path.
- Letting a stale process write `Aborted` for receipts it no longer owns: the successor's retirement already decides them in one transaction.
