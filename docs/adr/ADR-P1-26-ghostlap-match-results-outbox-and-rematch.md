# ADR-P1-26 — Ghost Lap durable match results, MatchFinalizedV1 and rematch
- **Status:** Accepted at Spec 10 task 10.4. Implemented and tested locally against real PostgreSQL 18 (evidence in `docs/kiro-log.md`). Relay delivery of `MatchFinalizedV1` to Redis and its Spec 12 consumer are NOT exercised here.
- **Scope:** how a finished multiplayer match gets exactly one truthful durable terminal decision, what the result contains, what is published, and how a room starts its next round. Builds on ADR-P1-24 (generation fence, start receipt, lock order) and ADR-P1-22 D11-D13 (terminal, placement, eligibility, rating id).

## Decision
1. **One transaction, one lock order.** `MatchAuthorityStore.FinalizeAsync` locks the receipt row (`FOR UPDATE`), requires `Started` under the caller's generation and that generation `Active` (`FOR SHARE`), then inserts `ghostlap.match_result`, inserts one `ghostlap.MatchFinalizedV1` row with the shared Outbox v1 writer (`PostgresOutboxWriter` over `MessagingTables("ghostlap")`, composed by `Hosts.Realtime`; the domain sees only the Kernel `IOutboxWriter` port), and moves the receipt to `ResultCommitted`, all on the same transaction. Retirement and the fenced abort keep the ADR-P1-24 order, so whichever locks the receipt first decides it.
2. **Answers.** A `ResultCommitted` receipt with the same digest is `AlreadyCommitted` (covers a lost commit acknowledgement); a different digest is `Conflict` and is never overwritten; an `Aborted` receipt is `Aborted`; another or a retired generation is `NotAuthority`; an unknown match is `NotFound`; any driver failure, including an unknown commit outcome, is `Unavailable` and is resolved by the next attempt reading the receipt.
3. **Database invariants (migration `ghostlap/0005_mp_results.sql`).** A result insert locks the receipt itself and is refused unless the receipt is `Started` under an `Active` generation (GL002); it must repeat the receipt's room, generation, config digest, rating algorithm id, roster and target tick, and its placements must satisfy `mp-placement-v1` (GL003). `Started -> ResultCommitted` requires the result and outbox rows already present (GL002). Deferred constraint triggers check at commit that a result has its `ResultCommitted` receipt and event, and that the event carries the same match, digest and document (GL003). At most one `MatchFinalizedV1` per match (partial unique index) and a deterministic event id (SHA-256 of the match id, RFC 9562 version 8 layout). Results are immutable and undeletable even for the owner (GL001); outbox business columns are immutable; nothing is deletable. So an `Aborted` receipt can never have a result or a rankable event.
4. **Result document `ghost-mp-result/1`.** Match, room, round ordinal, generation, config digest, rules/layout identity, seed (decimal string), target and final tick, final MP state hash, placement and eligibility policies, `ratedEligible` + reason, the sealed `ratingAlgorithmId`, and per slot: member id, guest principal, outcome (`finisher`/`forfeit`), forfeit tick, competitive placement, total/movement/pickup/penalty points, distance, pickups, final charge, Bursts, Burst hits landed, times hit by a Burst, contact drains suffered and charge lost to contact. The two contact counters and times-hit are folded from the resolved event stream by `MpMatchStats`; everything else is the final `PlayerState`. No client value enters it.
5. **Digest.** SHA-256 over a `CanonicalWriter` encoding with a fixed field order (players in slot order), not over JSON. The JSON (`System.Text.Json` web defaults) is a transport form; a consumer recomputes the digest from the parsed document (`MatchResults.Digest`). Tested: round trip keeps the digest; changing any significant field changes it.
6. **Placement `mp-placement-v1`** (ADR-P1-22 D12): competition ranking, `1 + number of players strictly ahead`, every finisher ahead of every forfeit, higher total ahead within a class; equal totals in a class share a placement (1, 1, 3). Slot order is display-only. **Eligibility `mp-eligibility-v1`**: `no_finisher` (all forfeited) and `fewer_than_two_guest_principals` are unrated; otherwise `eligible`. An unrated result is still a finalized result with its one event (Spec 12 records it without effect). A service-side abort produces no result at all.
7. **Finalizer outside the tick.** After tick 2700 the loop has ended; `MatchRegistry` builds the result and calls the store with bounded attempts (`FinalizeAttempts` 8, backoff 100 ms doubling to 2 s), only while `IRealtimeAuthority.IsValid`. Status is `pending_finalization` meanwhile; `finalized` only after a committed receipt with this digest was written or read; `aborted` only after an `Aborted` receipt was read; otherwise `unverified` (provisional, unrated, never presented as aborted). With no authorized finalizer left, the next generation's retirement aborts an uncommitted receipt (its durable decision); a committed result survives retirement.
8. **Reads.** Hub method `GetMatchResult(matchId)` returns `MatchOutcomeView` (`finalized` with placements, `aborted` with reason, or `pending`) to a member of the match's room or a principal of its sealed roster; unknown or foreign is `result_not_found`. It reads PostgreSQL when the result is not in memory, so it works after a Realtime restart. Member views carry no guest principal ids.
9. **Rematch.** Hub method `Rematch(RoomCommand)` (a competitor's controlling connection) returns a room whose match is settled (`finalized`, `aborted`, `unverified`) to the lobby: ready flags cleared, round ordinal + 1, previous match viewers detached, host re-picked if disconnected. It is refused with `finalization_pending` while the result is being decided, and is idempotent (`already_lobby`). The next round goes through ready/start and seals a fresh match id, seed and state; a new receipt row and its own result. The process generation stays the same within one process (it is process identity, not match identity).
10. **Relay.** `ghostlap_outbox_relay` (NOLOGIN) gets the shared OutboxRelay grants on `ghostlap.outbox` only. `migrate.sh` provisions `sands_worker_ghostlap` from `WORKER_GHOSTLAP_DB_PASSWORD`; `Hosts.Worker` registers `AddMarrowOutboxRelayService(..., "GhostLap:Relay", "GhostLapRelay", MessagingTables("ghostlap"))`, which is inert unless both settings exist. Compose wiring is not added (task 10.6).

## Contract compatibility
Additive: `MatchStatuses.Finalized` and `IsSettled`; `GhostLapWire.RematchMethod`/`GetMatchResultMethod`; `GhostLapFailure.FinalizationPending`/`ResultNotFound`; `RoomNotices.RematchLobby`; new records `MatchResultDocument`, `MatchPlayerResult`, `MatchFinalizedV1`, `MatchOutcomeView`, `MatchPlayerResultView`; `IActiveRoomOwner.Rematch`; `MatchAuthorityStore` optional outbox writer factory. `pending_finalization` now normally ends in `finalized` instead of staying until the next generation. `ghost-v1` bytes, codecs, rules and goldens are unchanged; Marrow and Revenant source are unchanged. No TypeScript twin yet (10.6). The `MatchFinalizedV1` payload is the Spec 10-owned contract that the Spec 12 design says must be coordinated before the rating worker is built; Spec 12 has not reviewed it yet.

## Rejected alternatives
- Inserting the result first and committing the receipt in a second transaction: a crash between them leaves a result without a decision.
- Recomputing placement or eligibility in the rating consumer: Spec 12 must verify, not decide.
- A random outbox event id: a retried finalization could then emit two events if uniqueness relied on the id alone.
- Treating a missing result after a crash as an abort: the receipt's decision is the only truth; `unverified` is reported until it exists.
