# R6 model-required Screening contract

R6 uses the V4 scheduler, PostgreSQL ledger and Marrow Timeline. The model-required source opens with the six-bank behavioral scenario, catalog v7, the existing human review policy, `risk-features-v2` and `BehavioralRiskScorerV2.PublishedPin`. The v8 child preserves the source's scenario origin and model pins. The original V4 rules-only context and payload formats remain valid.

`v4-model-screening-evidence/1` is the canonical Screening payload and the evidence schema. Both the SQL evidence reference and the V4 input envelope name its SHA-256. Its canonical format starts with an Int32 version and length-prefixed schema ID. In order, the payload contains the lineage UUID, logical intent ID, sequence and effective time, preceding sequence and digest, last seal, feature schema and vector bytes, optional vector digest/raw Single bits/integer PPM, model ID, ZIP hash, threshold, feature schema hash, calibration ID, inclusive threshold flag, base policy and decision, capacity version and counts, available and allowed slots, admission/suppression/overload flags, and final decision, payment status and case flag. Physical execution ownership remains in SQL. V4's existing prefix digest commits the payload hash without changing its digest algorithm.

The scheduler locks the physical run and chooses its earliest due command. The same transaction reads and folds its opening and fact journal. The model path locks the payment, source balance and cursor, and verifies them against the fold. `V4ObservationProjector.RiskAt` then takes the canonical prefix through the accepted Intent and every other preceding fact, including earlier facts at the same effective time. For a child it reads only closed ancestor prefixes through the recorded fork positions on the same transaction. The scorer consumes the canonical 70-column vector and verifies its digest. The single cached, validated R5 scorer applies its original sigmoid and inclusive 852,469 PPM threshold. The persisted evidence identifies the calibration contract; the model ID also commits the exact calibration coefficients.

Screening before the original 24-hour cutoff explicitly records `WarmupRulesOnly` with no score or vector. Thereafter, `v4-model-review-capacity/1` counts each completed Screening once. With the current opportunity included, the cumulative slot count is `floor(n / 20)`; available slots subtract previously admitted mandatory and learned holds, floored at zero. Mandatory v7/v8 holds have priority even when over budget. Warmup holds and rejections without a case consume no capacity. A learned review requires an above-threshold score, available capacity and sufficient funds for a legal reservation. When capacity is exhausted, a base-clear payment stays clear with its high-risk suppression recorded. When funds cannot support a learned hold, the model cannot reject the payment; normal base-clear processing applies. A mandatory hold that cannot reserve funds retains the existing insufficient-funds rejection.

The application validates evidence before applying existing ledger transitions. SQL commits the canonical fact, audit, outbox, payment and case writes, reservation, cursor and command outcome together. The capacity policy is derived and stored from the immutable SQL context at opening. Counters fold from recorded facts. Model checkpoints retain the three cumulative counts in a versioned extension between the inherited ledger bytes and the existing clock and digest trailer. PostgreSQL checks that trailer and the full checkpoint hash when binding a fork. Existing rules-only checkpoint bytes are unchanged. Counts do not reset on fork and are not returned after review. Inference and configuration failures block the due command with distinct outcome codes. An explicit scheduler retry re-reads the prefix; permanent artifact/configuration failures require operator remediation. A conflicting or invalid prefix aborts the transaction.

Synchronization uses existing deterministic Marrow operation keys. Cold replay validates the evidence reference, binding, model and rule pins, decision and capacity without ML.NET. An independent feature audit via `V4ObservationProjector.Project(history, captureRisk: true)` rebuilds and compares post-warmup vector bytes. Existing bank, account and settlement target projectors retain their financial meanings.

The native financial checkpoint requires an actual reservation, open case and verified cold replay. The published Worker registers the V4 Timeline, store and dispatcher with a singleton lazy R5 scorer. It takes the ledger writer from `ConnectionStrings:RevenantLedger` and the Timeline engine from the existing restricted `ConnectionStrings:Postgres` composition. `--v4-dispatch <physical-execution-uuid> <step-count>` advances a bounded number of scheduler steps for the configured ledger tenant, then synchronizes the committed journal. A count of zero reconciles after interruption. The published Worker integration test exercises the same command and service registration against disposable PostgreSQL. The v7-to-v8 fork proof verifies identical checkpoint bytes, child-owned balances and cases, independently scored suffixes, inherited capacity, and predictor-free replay. R8 can use `V4BranchExecution.OpenSourceAsync`, `ForkAsync`, `SynchronizeAsync` and `ReadProjectionHistoryAsync` with the existing scheduler admission and execution methods.

R7 can consume the existing `V4ObservationProjector.Banks`, `Accounts`, `AccountAsOf` and `V4BankTargets.Build` APIs. The paired qualification verifies that holds increase reserves, settlements alone change posted flow, and missing target horizons stay masked. The [native evidence report](r6-live-financial-ml-evidence.md) identifies the captured series and how to regenerate it.
