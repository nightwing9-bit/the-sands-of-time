# R3 branch execution contract

A root shares its canonical lineage and SQL execution UUID. A child keeps that lineage in its state, canonical inputs and input IDs. It owns a different SQL execution UUID and a different Marrow Timeline ID. The Marrow rules hash covers the V4 schemas, scheduler, observation contract and cadence. The V4 contexts pin the catalog v7 and v8 rules-only policies.

Migration `0010_v4_branch_execution.sql` stores tenant, execution, lineage and Timeline IDs, the source execution and Timeline IDs, fork sequence and boundary, 32-byte state and prefix hashes, the context hash, the operation key and readiness. The operation is unique in its tenant. The reservation persists the full request before the Marrow fork. A pending row has no child Timeline binding or scheduler. A retry must match the reservation and uses the same Marrow operation key. The transition to ready, child opening, cursor and scheduler commit together. The SQL triggers check the source seal and exact Marrow origin without granting the ledger writer Marrow table access.

The child cursor starts at the fork position `k`. Its scheduler clock and watermark start at the fork boundary and retain the scenario origin. The first physical suffix fact is `k+1` and uses the digest after source seal `k`. Further facts use the immediately preceding sequence, including when effective times are equal. The child command digest starts from its own execution UUID. The original V2/V3 cursor counts and R2 unbound scheduler retain their zero base.

The materializer takes posted balances and active reservations from the verified checkpoint. Physical accounts, payments, cases and approvals have new IDs. Imported payment trails and approval slots stop at the counts in the checkpoint. Inherited posting references have no new debit or credit entries. Opening balances already include those amounts. The child can use an inherited settlement reference for a later compensating return.

The scheduler locks its run first, selects the due head, and the ledger then takes any required payment, case and ordered account locks before advancing the cursor. A single SQL transaction writes the ledger effects, audit, outbox, canonical fact, cursor and command outcome. SQL checks that a completed command and its matching fact commit together. The dispatcher folds the canonical state and compares posted, reserved and available SQL balances before committing a financial fact. The clock assigns the command's due time. At the exact boundary the seal comes first.

`V4BranchExecution.SynchronizeAsync` folds the durable SQL fact journal from the verified Timeline origin and appends with deterministic operation keys. It verifies stored prefix digests, prior receipts and the resulting Timeline bytes. The SQL transaction and Marrow append are separate. A SQL commit can therefore leave the Timeline behind until synchronization runs. Closure freezes SQL, then synchronizes and verifies Marrow. Forking requires a closed source and a verified Timeline through the final SQL cursor. The fork uses the verified checkpoint at the requested earlier seal.

For R4, the existing internal entry points are `V4BranchExecution.OpenSourceAsync`, `ForkAsync`, `SynchronizeAsync`, `CompleteAsync`, and `V4SimulationStore.AdmitAsync`, `AdvanceOneStepAsync`, `SealAsync` and `ReadJournalAsync`. Use a store composed with `PaymentLedgerStore` for finance. Exogenous intake carries the existing canonical PaymentIntent with the lineage UUID and due time. Derived screening and settlement opportunities carry the logical intent ID. The trusted caller supplies verified human requests, and dispatch rechecks the branch's staff scope, case version and review rules. Derived outcomes are evaluated from the branch's state. The tested branch continuation admits the same intake independently and re-evaluates conditional human requests. Model-required finance remains outside R3.
