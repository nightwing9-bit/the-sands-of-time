## 9. Source ledger, replay, model and Worker runtime risks

- **Amount and posted balance.** The authoritative boundary for scoring remains screening. Intake observes the committed balance under cursor serialization, then releases it. Any later lawful balance change can alter the feature input, so `InferAsync` reacquires the source-account lock and cursor and rebuilds features. Regular Friday Ring opens with 66,000,000 minor units total. Balanced intra-run postings conserve the sum and spending checks prevent negative available balances. Under those existing rules a normal account cannot rise past 2^53. The SQL-seeded fixture represents an out-of-domain account, rather than a production funding route. A future larger funding route would need explicit treatment. No extra lock, clamping, new finance fact or auto-resolution is present.
- **Queue and closure.** The V3 claim predicate checks earlier Initiated intent facts even when a concurrent transaction holds their payment row. Once a head fails, the pass excludes that run and can select other runs. The run is eligible for reassessment next pass, including a balance that returns to the supported range. A permanently incompatible legacy amount stays Initiated and closure remains blocked by design. Operator warnings and a pause make this visible, but repeated scans over many blocked runs remain a cost risk. Real PostgreSQL proof is still required.
- **Cold replay.** The child launches another PID with a distinct artifact directory, zero predictor registrations and a deployed replay/projection login. Its SQL checks table and column privileges on named live relations. It retains valid Timeline privileges so the proof depends on source verification and exact before/after comparisons, not on a read-only database. An actual process launch must still validate dependencies, grants, child output and final reconciliation.
- **Model and runtime.** Original scorer identity and integer scoring are preserved. In the 5.0.1 Linux AMD64 package, prior ELF inspection showed `libMklImports.so` needs glibc and `libiomp5.so`, and the packaged proxy depends on MKL imports. The Worker recipe uses Noble glibc with LLVM OpenMP via the alias. Prior registry inspection established both pinned Microsoft tags and AMD64 manifests.
