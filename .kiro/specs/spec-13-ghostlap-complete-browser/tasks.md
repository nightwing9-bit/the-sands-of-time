## How this spec is executed

**One game, one art direction.** The installed `design-inputs/ghost-lap-frontend-director/SKILL.md` and its references `00`–`12`, the user's actual `design-inputs/game-assets/characters.md`, approved source assets, and verified Specs 10–12 are required reading. The skill owns approved presentation; real source code/DTOs own game truth. Its *CONFIRMED* rules and negative catalogue are hard boundaries. Its *DIRECTOR BASELINE* values are excellent starting points—not an instruction to spend hours optimizing an unplayed guess.

**Primary creator: Claude Opus 5.5.** Use **High** for original world composition, character acting, material/shader art, signature timeline and cinematic time travel. **Medium is acceptable for bounded implementation using an already-established design**—for example wiring menus, straightforward audio state routing, history lists, settings or well-understood HUD work. Escalate to High when a real creative/technical problem calls for it. Never dilute the approved vision merely to save credits. Equally, do not spend High on long tool runs, generic scaffolding, tuning numbers nobody has listened to, or repetitive repairs.

**Codex is outside this task checklist.** Do **not** launch a standing B1–B5 program from Kiro or reproduce a large Codex test plan here. When a task needs backend DTO/proxy/geometry work, asset processing, mechanical implementation, browser setup, or substantial verification, **stop at the narrow boundary and report the exact need to the main agent**: source file, observed mismatch, required behavior, smallest success check, and whether the current creative slice can continue. The main agent will decide whether to issue a focused Codex Medium prompt. Codex may be used more than once, including for tiny jobs. Opus does not independently redesign the backend to avoid an external handoff. No automatic Codex work is implied by merely mentioning a dependency.

**Human taste is part of the loop.** Do not aim for a fictional “perfect” mix, slider position, screen feel or cinematic pacing from reasoning alone. First implement a convincing, source-faithful version; show it *in the actual running app* as soon as there is something meaningful to judge; collect the user's specific response; correct it at the owning component. **Do not build several irreversible UI systems before the user can see/play them.** In early world/character tasks, execute the user's already-settled art direction confidently rather than repeatedly asking taste questions. Later interaction/audio/pacing tasks deliberately favor a solid first pass and prompt user play over speculative hyper-polish.

**One simple live-preview workflow.** Reuse the verified `web/apps/ghost-lap` Vite application. Once a browser preview is available, keep using **the same reachable dev URL with hot reload**, not a new mockup site or a separate preview framework for each task. If a working preview cannot remain alive across agent sessions, provide an accurate reproducible start instruction and current URL, not a promise of a persistent server. The user should be able to refresh and test the latest change. Dev-only controlled state samples are acceptable to inspect expressions/FX; they must be visibly marked as **preview fixtures**, use actual approved art/realistic source-backed data, and must never masquerade as successful real gameplay. Gameplay acceptance requires real authority.

**Per-task review loop (lightweight):**
1. Read only the relevant skill references plus recorded decisions and real code for that slice; do not reread the entire 19k-word skill every session.
2. Implement the smallest **complete, beautiful, reusable slice**. Preserve existing artwork, source masters and previously approved composition.
3. Make it viewable in the existing app. Do one focused sanity check (and an actual short play/listen when appropriate), not a broad regression suite.
4. Report **what changed, what URL/action the user can try, two or three questions worth judging, and exact defects/dependencies**. Mark **HUMAN REVIEW PENDING** until the user actually responds; never claim a subjective approval on the user's behalf.
5. Apply reported preferences with a small correction pass before further design choices would make them expensive. If review cannot happen immediately, record the provisional decision and avoid baking it into unrelated components.

**Status honesty:** An Opus slice may be **CREATIVE IMPLEMENTATION DONE / HUMAN REVIEW PENDING / TECHNICAL ACCEPTANCE PENDING** independently. Check a task only when its specified implementation and readily available focused correctness gate have actually passed; list pending human or Codex certification separately. The entire Spec 13 cannot be declared accepted without authentic browser journeys, real history correctness, source-asset/distribution clearance and a user-observed experience. Do not invent CI success, license grants, FPS measurements or a saved run.

**Never change:** Marrow; `ghost-v1`, `ghost-mp-v2` or `arena-v1` simulation semantics; scoring/collisions/Burst; canonical records; ghost replay; owner authorization; fork T semantics. No mobile/touch controls, global leaderboard, social profiles/chat/Elo, public replay sharing, AI opponents, or nested child forks. The timeline appears in historical contexts, **not all screens**.
